# 原型优先 UI 开发契约

## 适用范围与决定

适用于 DianMao 的全部 Android UI:页面、导航、全屏次级页、对话框、共享组件、状态反馈与可见交互。

开发约定:

1. **所有 UI 必须基于已确认原型**;缺少页面、交互或必要状态时,先补原型并经用户确认,不得直接实现 Compose。
2. **已确认原型是唯一视觉基准,实现必须与原型一致。** 正式 Android UI 以「像素级对齐已确认原型」为目标:同一页面在同数据、同状态下,与原型应用区域(手机内画面)不应有可见差异。

这是强制开发契约,不代表 Android 已完成迁移,也不代表原型里的演示能力全部批准为新功能。

阅读入口:`design/mockup/BASELINE.md` → 任务 PRD / research → 已确认原型场景 → 本规范 → `design/mockup/README.md`、`DESIGN.md`、`.trellis/spec/backend/compose-patterns.md`。

## 0. 像素级对齐铁律(最高优先级)

**用户明确要求(2026-10-11):参照原型进行像素级 UI 更新,保证软件界面与原型一致。** 以下为硬约束:

1. **原型是像素级参照物。** 逐屏对照原型应用区域实现,而不是「大致参考」。布局、间距、字号、字重、圆角、颜色、透明度、图标、文案、块顺序均以原型为准。
2. **任何可见差异都是缺陷,** 除非它属于下方第 0.1 节的「允许偏差」并已记录。不接受「看起来差不多」。
3. **先对照再写代码。** 实现一个页面前,先把原型该屏与当前 Compose 该屏并排看一遍,列出差异清单,再改。
4. **一次一屏,附带截图。** 每完成一屏即产出「原型 vs 实现」同尺寸并排截图作为证据;无截图不算完成。
5. **不自行发挥。** 不新增原型没有的元素、按钮、文案或动效;不因「更原生」「更好看」而改变已确认的视觉。若认为原型有误,先改原型并取得确认,再同步实现。
6. **原型改动即视为基准变更。** 实现期间一旦发现需要偏离原型,回到「先改原型 → 用户确认 → 再改实现」的流程,禁止两处各自漂移。

### 0.1 允许的偏差(必须逐条记录)

仅以下情况可偏离原型,且必须在任务的 `research.md` 或验收表中逐条记录原因:

| 偏差类别 | 示例 | 要求 |
|---|---|---|
| 单位换算 | 原型 `13px` → Compose `13.sp`/`13.dp` | 按 1px≈1dp/1sp 映射;系统字体缩放时以 sp 为准 |
| 触摸热区 | 原型 34px 图标钮 → 视觉 34dp + 48dp 可点区 | 视觉尺寸不变,扩展热区 |
| 平台原生控件 | M3 `DatePicker`/`TimePicker`/`Switch` 的实际渲染 | 原型已按真实形态绘制;若系统版本渲染有细微差别,记录并保留 |
| 安全区域 / insets | 状态栏、导航栏、键盘 | 原型手机边框内为安全区;实现按 `safeDrawing` 处理 |
| 字体可用性 | 字重或字形缺失时的最近回退 | 记录回退项 |
| 数据驱动差异 | 真实数据阈值、数量、文案长度 | 结构一致,内容随真实数据 |

**不属于允许偏差**(必须修到与原型一致):颜色、间距、圆角、层级顺序、块结构、文案、图标选择、阴影/边框强度。

## 1. 权威边界

- **原型只能画能 1:1 复刻到 Compose 的 UI。** 平台原生控件(Material 3 `DatePicker`/`TimePicker`、系统选择器、权限弹窗)必须按真实形态呈现,不能自创更“好看”但实现不了的交互。无法复刻的控件不画;宁可简单,不可失真。
- 已确认原型决定视觉与交互意图:配色、层级、结构、组件和操作路径。
- 真实业务契约决定数据和操作后果。模拟原型不能覆盖 Room 持久化、日历写入、警报调度、WebDAV 备份、权限等行为。
- Android 安全区域、系统返回、权限弹窗、系统选择器、无障碍优先;显著布局/流程偏差必须说明并经用户确认。
- 不移植预览外壳(左章节导航、手机外框、模拟状态栏、明暗切换按钮)与演示成功逻辑。
- 原型与既有功能冲突时先补原型,不得任意二选一或默默删掉功能。

## 2. 强制变更流程

1. 列出受影响页面、组件、交互和状态,找到可操作的已确认原型入口(`design/mockup/`)。
2. 对照现有 Compose 代码区分:已有能力、原型漏项、原型新增能力、原生差异。
3. 缺少任何必要 UI 时先补原型;已有基准的修改需记录改了什么。
4. 用户明确确认新增/修改的原型范围,记录到 `BASELINE.md` 或任务决策记录中。
5. 才能实现 Compose;执行任务仍需通过 Trellis 规划评审与启动门槛(`task.py start`)。
6. 对照截图与真实交互验收;变更原型及实现时同步更新状态表与规范。

只批准「开始规划」不等于批准未见过的原型补充,也不等于批准正式实现。禁止开发完成后再倒补原型作为形式手续。

## 3. 基准与版本记录

- `design/mockup/BASELINE.md` 保存原型标识、来源文件、确认范围、待补项、文件 SHA-256 及后续确认记录。
- 原型入口 `design/mockup/` 下的 `index.html`、`style.css`、`app.js` 必须纳入 Git。未提交时记录文件 SHA-256,提交后记录实际基准 commit;不得虚构版本。
- 修改原型即产生待确认差异。不能因为目录名不变就沿用旧确认;用户已批准的未修改部分仍有效。
- 截图只是证据,已确认的 HTML + CSS + JS 场景才是基准;手机展示外框不属于应用验收区域。
- 设计令牌权威来源是 `DESIGN.md` 与 `app/src/main/java/fun/han1997/dianmao/ui/theme/DianMaoTheme.kt` / `DianMaoTokens.kt`;原型 CSS 必须与之一致,出现原型里有、主题里没有的颜色即为缺陷。

## 4. 每项 UI 的交付记录

任务 PRD / 验收表必须包含以下字段,可一项一行:

| 字段 | 内容 |
|---|---|
| UI 标识 | 页面/组件 + 场景名,例如 首页 / 搜索无结果空态 |
| 原型入口 | 文件与操作路径,不能只写「参考原型」 |
| 功能归属 | 已有能力 / 本任务新增 / 其他任务 / 演示专用 |
| 确认状态 | 待补 / 待确认 / 已确认,并记录确认依据 |
| Android 映射 | 对应 Screen、组件、ViewModel/状态来源 |
| 状态覆盖 | 正常、加载、空、错误、禁用、进行中、确认等 |
| 平台偏差 | 无 / 明确理由与审批依据 |
| 验收证据 | 同场景明暗截图、交互检查、未完成原因 |

例:事项详情 / 完成历史折叠 → 原型 `事项详情` 页折叠组件 → 复用 `CompletionHistoryGroup` → 展开/收起两态截图;不能照搬原型把折叠态当作唯一状态。

## 5. 完整状态与保留功能

- 页面:初次加载、内容、无数据、无搜索结果、错误/重试、刷新有旧内容。
- 操作:可用/禁用、执行中(防重复点击)、成功/失败、选择/取消选择。
- 危险操作:说明真实影响,确认只执行一次;取消不得执行;沿用 `QuietDialogContainer` 家族与错误色确认按钮。
- 既有功能即使原型未画也必须保留:批量操作、长按拖拽排序、滑动完成/删除、日历移动、子事项、重复规则、到点提醒提前量、桌面小组件、通知快捷操作等。原型新增但未批准的按钮不进入正式版本;不得保留可点击却只给假成功的入口。
- **不做演示数据播种,首启即真实空态。** 原型 `initial()` 里的示例任务是原型自身的演示状态,**不得**当作产品行为移植:`TaskRepository` 不得有 `seedIfEmpty` 之类的首启注入,`TaskDao.countTasks()` 这类只服务于播种的查询也不得保留。新安装首次打开必须走真实的空状态分支(首页四象限板与智能视图各自的 first-run 引导 + 「新增事项」CTA),这也是「空态」验收的唯一场景。
- 主题:明色与暗色都必须覆盖;`DianMaoTheme.kt` 的 `lightColorScheme`/`darkColorScheme` 是唯一权威。

## 6. Token 与组件

- 继续使用 `ui/theme/`、`ui/components/`、`ui/panels/`、`ui/screens/`,不新增平行主题或第二套形状/颜色常量。
- 原型的 CSS 角色先映射到 Compose 语义角色(`primary` / `secondary` / `surfaceVariant` / `outline` …),再集中调整值;禁止每个页面直接复制十六进制颜色和局部阴影。
- 透明度使用 `DianMaoAlpha`(`subtle` / `boardPane` / `muted` / `mutedText` / `strong`),不散落魔法值。
- 原型确认后的值变更替代旧视觉值,但不替代业务状态语义。
- px 不能机械等同 dp/sp。系统字体、48dp 热区、字体缩放与 insets 必须兼容;例如 40px 图标按钮可保留视觉尺寸但扩展触摸区域。
- 象限色只作用于低透明度底纹(首页 4.5%、象限头/空态 8%)与指示点;日历蓝只用于时间语义。局部偏差要记录,不能以「原生适配」为由自行重设计。

## 7. 验收门槛

**编译通过不等于 UI 验收通过。** 必须完成:

- **像素级并排比对**:同一页面、同一数据、同一状态,原型应用区域与实现截图并排;需列出并关闭所有可见差异,或逐条登记为允许偏差。
- 明色/暗色各一组 Compose 预览或运行截图。
- 至少验证 320dp、390dp 和更宽窗口;字体 1.0 与 1.3/2.0;长文本、键盘展开、系统返回和安全区域。
- 可访问名称、可读对比度、48dp 热区、非颜色状态提示、减弱动画;原型侧支持键盘焦点与 `prefers-reduced-motion`。
- 检查共享组件改动的所有调用方,不只截图当前页面。
- 执行 `:app:testDebugUnitTest` / `:app:lintDebug` / `:app:assembleDebug` 与 `git diff --check`;原型冒烟测试不能替代 Android 测试。
- **不使用模拟器/真机做验收(用户指令 2026-10-13:「永远不要使用模拟器了,没必要」)。** 验收的上限是:上述 Gradle 检查 + 原型冒烟测试 + 原型侧明暗/断点截图。不要在实现侧启动 AVD、`adb install` 或截屏;若某状态只能在设备上确认,登记为「设备侧未验证」的残余风险交用户自行确认,**不得**据编译通过声称视觉验收完成。
- 无设备/依赖下载失败时记录「未验证/阻塞」,不得声称视觉或发布验收完成。

## 错误与正确做法

| 错误 | 正确 |
|---|---|
| 原型没有某状态,于是删掉该功能 | 先补原型与确认,再迁移既有能力 |
| 原型画了自创的时间步进器,而正式实现是 M3 `TimePicker` | 原型直接画 M3 表盘 + 键盘双模式,与实现同源 |
| 原型演示「已连接」,正式界面直接显示同样状态 | 读取真实同步/备份结果,按结果展示成功或错误 |
| 原型 `initial()` 有演示任务,于是实现里播种一批 | 首启即真实空态,示例数据只属于原型 |
| 每页复制 `#A84534` | 使用 `MaterialTheme.colorScheme.primary` 或 `DianMaoTokens`,从统一 token 读取 |
| 原型新增区块,于是直接扩大开发范围 | 先确认范围,未批准的按钮不进入正式版本 |
| 只编译通过就标记 UI 完成 | 明暗截图、完整状态、交互与目视验收通过才算完成 |
| 原型改了颜色但主题没同步 | 同步更新 `DianMaoTheme.kt` / `DESIGN.md`,两侧一致才算基准 |
| 实现「大致像原型」就交付 | 逐屏并排比对到无可追可见差异,或逐条登记允许偏差 |
| 实现时觉得原型某处不好看就自行改 | 先改原型并取得确认,再同步实现 |
