# 继续完善核心任务体验

## Goal

在上一轮 UI 优化基础上，继续提升 DianMao 的日常任务处理效率与交互一致性。重点不再是大面积换肤，而是修复当前核心流程中仍然存在的状态闭环问题，让时间设置、重复提醒、任务完成、子事项编辑、删除/归档和异步反馈更容易理解、更难误操作。

## What I Already Know

* 项目是单模块 Android Compose 应用，核心工作流仍集中在 `MainActivity.kt`。
* 上一轮已经优化主页搜索无结果、任务行更多菜单、任务详情纵向操作、任务表单保存反馈和协程取消处理。
* 当前任务表单在没有日期时禁用日历和响铃，但重复规则选择器仍可能保持可用；清除日期时会清除日历和响铃，但需要验证重复规则状态是否同步清理。
* 任务完成、子事项切换、归档、删除、完成记录编辑/删除等操作分布在多个回调中，部分异步操作缺少统一的进行中或失败反馈。
* 当前主页四象限内的紧凑任务预览主要用于扫描，点击象限后才进入可操作任务列表；任务行的 48dp 完成区域和更多菜单已经具备基础可访问语义。
* 现有 JVM 测试覆盖时间关注、重复提醒、返回优先级和日历选择，但尚未覆盖表单状态约束或操作反馈状态机。

## Assumptions

* 本轮优先解决直接影响正确性和日常效率的交互逻辑，再做少量对应的视觉提示，不进行新的页面架构设计。
* 不改变任务数据模型、备份格式和四象限产品模型。
* 继续复用 Snackbar、现有表单组件、TaskRepository 和既有纯函数测试方式。

## Requirements

* 让时间、日历、响铃和重复规则形成一致的依赖关系：没有日期时不能启用相关能力；清除日期时同步清除所有依赖时间的选项；重复规则不能在响铃关闭时留下看似有效的状态。
* 对完成任务、子事项切换、归档、删除和完成记录修改等高频异步操作提供清晰的成功/失败反馈；普通失败不得静默，协程取消不得被转成业务失败。
* 任务完成入口需要明确区分“完成并写心得”和已完成任务的“编辑心得”，避免用户误解点击后的行为。
* 任务详情和表单在窄屏、长标题、长子事项和系统字体放大时保持关键按钮可达；操作区不因文本挤压而裁切。
* 对重复任务完成后的当前周期状态、提醒重新调度和取消提醒路径进行回归检查，必要时补充纯逻辑测试。
* 保持现有任务行结构，不增加常驻多按钮操作栏，不引入新的第三方依赖。

## Acceptance Criteria

* [ ] 表单中日期、响铃、日历、重复规则的启用和清除行为一致，状态不会出现“看起来已设置但实际不会执行”的组合。
* [ ] 完成、子事项、归档、删除和完成记录操作在成功与失败时都有可理解反馈，且本地保存结果与平台副作用失败分开表达。
* [ ] 重复任务完成/取消完成后，当前周期、提醒调度和界面展示没有回归。
* [ ] 长文本与大字体下，表单保存、详情完成、归档、删除和返回操作仍可见且可触达。
* [ ] 新增或修改的纯逻辑规则有 JVM 单元测试覆盖。
* [ ] `:app:testDebugUnitTest`、`:app:lintDebug`、`:app:assembleDebug` 和 `git diff --check` 通过。

## Definition of Done

* 代码审查发现的问题已转为可验证需求并实现。
* 相关测试、lint、debug 构建和 diff 检查通过。
* 用户可见行为更新到 `CHANGELOG.md`。
* 若形成新的错误处理或状态约束，更新对应 backend spec。
* 仅提交本任务产生的代码、文档和规范变更。

## Out of Scope

* 不重做主页视觉主题或整体导航。
* 不新增标签、项目、账号、协作或云同步。
* 不修改 Room schema、备份 JSON 结构或提醒协议，除非审查证明现有行为无法在当前模型内修复。
* 不改动 `.impeccable/` 和 `.opencode/` 用户配置。

## Technical Approach

先提取或复用纯状态约束函数，保证表单联动和重复任务边界可测试；再集中梳理 `DianMaoApp` 中的异步操作回调，使用统一的状态消息反馈，并在每个 `catch` 中保留协程取消语义。最后对任务详情和表单的操作区做最小的响应式调整，避免以增加视觉密度换取可发现性。

## Decision (ADR-lite)

**Context**: 第一轮已经改善了主要视觉层级，但部分设置联动和异步操作仍存在分散处理，可能导致状态残留或用户不知道操作是否成功。

**Decision**: 采用“状态约束先行、反馈统一、布局最小调整”的第二轮优化方案。优先修复可验证的行为问题，再补充必要的 UI 提示和测试。

**Consequences**: 日常操作会获得更可靠的反馈和更一致的时间设置语义；不会引入新的持久化状态，因此风险和迁移成本较低。
